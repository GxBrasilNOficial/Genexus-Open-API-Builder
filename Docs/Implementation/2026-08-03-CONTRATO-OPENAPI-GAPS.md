# Contrato OpenAPI - Divergências entre YAML gerado e comportamento real

## Objetivo

Corrigir, quando controlável por API pública do Extensibility SDK, as divergências entre o contrato OpenAPI que o GeneXus gera para o API Object e o comportamento real da API, e caracterizar como limitação, com evidência, o que não for controlável.

Esta frente não tem ID de backlog. Ela nasceu da conferência do YAML gerado que aprovou B047, B074, B075 e B078, registrada como frente própria porque as divergências encontradas exigiam mudança de geração, não verificação.

## Origem

Conferência por leitura direta, em 2026-08-03, de `apiNotaFiscal.yaml` nos dois environments da KB de teste `wsEducacaoSpTeste`, além dos YAML das quatro APIs anteriores da mesma KB e de uma API construída manualmente pelo usuário, usada como controle.

Cinco divergências foram levantadas:

1. cada operação declara apenas `200` e `404`, enquanto o runtime devolve `201` em Create, `400` na validação de obrigatório e `422` em erro de regra de negócio;
2. o schema de erro expunha `Errors[]` com subestrutura `Code`, `Message` e `Field` que a geração nunca preenche;
3. `requestBody` declarado com `required: false` em Create e Update, que exigem corpo;
4. schemas de request sem bloco `required:`, apesar de a validação com `400` existir em runtime;
5. `info.description` expunha a sentinela interna de ownership, com IDs de backlog, na documentação pública.

## Fonte da geração do YAML

O YAML não é escrito pela extensão. É produzido pelo gerador do GeneXus a partir de templates StringTemplate da instalação:

- `Packages/RestDLTemplates/Swagger.Yaml.stg` - paths, operações, segurança, `requestBody` e respostas;
- `Packages/RestDLTemplates/TypeDefinitions.Yaml.stg` - schemas dos SDTs e o bloco `required:`.

A extensão atua apenas sobre objetos, propriedades, anotações, variáveis, SDTs e Procedures. A regra de nunca escrever o arquivo YAML diretamente permanece.

## Resultado por divergência

| Divergência | Situação | Onde se resolve |
| --- | --- | --- |
| 1 - códigos HTTP declarados | limitação do gerador | não controlável |
| 2 - `Errors[]` nunca preenchido | corrigido | `sdt_API_ErrorResponse` |
| 3 - `requestBody: required` | corrigido | propriedade `Required` na variável do API Object |
| 4 - `required:` no schema | limitação do gerador | não controlável |
| 5 - sentinela no `info.description` | corrigido | `Description` do API Object |

## Correções aplicadas

### Corpo de erro sem array fantasma

O nível `Errors` foi removido da definição do SDT compartilhado `sdt_API_ErrorResponse`, que passa a expor somente `Code` e `Message` - exatamente o que a geração preenche desde B071-B073/B079, quando a IDE rejeitou a validação da Procedure com `ErrorItem` de subestrutura SDT e o erro público passou a ser top-level.

O SDT é compartilhado por todas as APIs geradas na KB e é reconfigurado a cada execução, então a mudança de forma alcança as APIs já geradas na próxima regeração. O schema derivado `sdt_API_ErrorResponse.Errors_Error` deixa de existir no contrato.

O reconhecimento de Procedure legada que ainda contenha `&ErrorResponse.Errors.Add(&ErrorItem)` foi **preservado**. Esse texto nunca é gerado: ele existe apenas como uma das variantes que o preflight reconstrói para identificar Procedures próprias de tentativas anteriores. Removê-lo faria uma Procedure antiga ser classificada como objeto de terceiros e bloqueada, quando o caminho correto é reconhecê-la como própria e regravá-la no contrato atual.

### Corpo da requisição declarado como obrigatório

O template emite `requestBody: required: $if(procedure.HasRequiredParameters)$true$else$false$endif$`. O modelo REST alimenta `HasRequiredParameters` a partir da propriedade pública `Required` - id interno `idVarServiceRequired`, descrita em `Definitions/SDTITEMDefinition.xml` e `Definitions/ATTDefinition.xml` como *"Value is Required when the variable is a service parameter"*.

A geração passou a marcar essa propriedade nas variáveis `&CreateRequest` e `&UpdateRequest` **do API Object**, com `Variable.SetPropertyValue`, protegida por `ContainsPropertyDefinition`.

A marcação precisa ser repetida em dois writers. O `ApiPlanBusinessComponentWriter` a aplica ao sincronizar Get/Create/Update, e o `ApiPlanListProcedureWriter` a reaplica porque recria todas as variáveis não padrão do API Object ao sincronizar `List`, etapa que roda depois e, sem isso, apaga a marcação.

### Descrição pública sem identificador interno

A `Description` do API Object, copiada pelo gerador para `info.description`, deixou de conter IDs de backlog. O formato passa a ser:

```
REST API for <Transaction>, generated by Genexus Open API Builder.
```

A string continua acumulando dois papéis: documentação pública e sentinela de ownership comparada por igualdade exata em `ApiPlanApiObjectWriter`, `ApiPlanGenerationStateReader`, `ApiPlanBusinessComponentWriter`, `ApiPlanListProcedureWriter` e `ApiPlanMetadataFileWriter`, além de ficar registrada na integridade B067.

A troca foi feita **sem lista de sentinelas compatíveis**, por decisão explícita do usuário: as APIs existentes estavam todas em KB de teste e seriam regeradas. API gerada com a sentinela anterior deixa de ser reencontrada e precisa ser apagada e regerada.

Separar os dois papéis - ancorar ownership apenas na metadata B067 e liberar a `Description` para edição - permanece como possibilidade de frente futura, não coberta aqui.

## Limitações caracterizadas

### Códigos HTTP declarados

O bloco de respostas de método de API Object é literal no `Swagger.Yaml.stg`:

```
procedure_responses(object, procedure, formatinfo)::=<<
responses:
  200:
    description: "Successful operation"
    ...
  404:
    description: "Not found"
>>
```

Não há propriedade, anotação ou ponto de extensão que altere esse conjunto. Códigos adicionais - `201`, `400`, `409`, `500` - aparecem apenas em dois casos que não são o nosso: o REST automático de Business Component, pelos templates `bc_responses*`, e o endpoint de upload `gxobject`, pelo template `post_gxupload`.

Evidência complementar: o `400` e o `500` presentes em `apiGuiaPed.yaml` vêm do endpoint `/apiGuiaPed/gxobject`, criado pelo GeneXus porque a Transaction tem campo binário, e não de nenhuma operação gerada por esta ferramenta. Nenhuma das cinco APIs geradas na KB de teste produziu código diferente de `200`/`404` em operação própria. A API construída manualmente pelo usuário na mesma KB também não.

Consequência prática: um cliente gerado a partir do contrato pode tratar como inesperada a resposta `201` de Create, que é o comportamento correto do runtime.

### Bloco `required:` nos schemas

O `TypeDefinitions.Yaml.stg` emite o bloco quando `level.RequiredAttributes` não é vazio. A propriedade `Required` do item de SDT **não** alimenta esse ponto do modelo REST.

Isso foi verificado, não suposto. Uma sonda temporária releu do modelo, depois de todas as gravações, o valor persistido em cada item, e registrou `Required='True'` nos dois membros obrigatórios de `sdtNotaFiscal_API_UpdateRequest`. O mesmo Build All que produziu `requestBody: required: true` continuou sem emitir `required:` no schema. Gravação e persistência funcionam; o gerador ignora.

A propriedade também não aparece no painel Properties da IDE para item de SDT baseado em atributo, porque um `customVisibleResolver` a oculta. Ausência no painel não indica ausência no modelo, e por isso a inspeção visual não serve de evidência aqui.

Como a propriedade não produz efeito, a marcação em item de SDT foi removida da geração. Escrever estado inerte e invisível em objetos da KB do usuário não se justifica.

Consequência prática: a obrigatoriedade de campo continua sem expressão no contrato. O consumidor descobre por tentativa e erro, recebendo `400`.

### Semântica de `required` quando ele é declarado

Onde o contrato declara obrigatoriedade - hoje somente no `requestBody` - vale a ressalva de semântica já registrada na `Emenda técnica — 2026-08-03` do registro de decisões do MVP e na nota de revisão de B076: em OpenAPI, `required` afirma **presença de membro**, enquanto o runtime valida **preenchimento**. Um payload com o membro presente e valor default do tipo satisfaz o contrato e ainda assim recebe `400`.

A divergência é assumida. O contrato é mais permissivo que o servidor, nunca o contrário.

## Atribuição das causas

Três execuções na IDE isolaram o que produz cada efeito:

1. primeira execução - marcação em item de SDT e em variável do API Object; a variável do API Object foi sobrescrita pelo `ApiPlanListProcedureWriter`; `requestBody` saiu `false`;
2. segunda execução - marcação adicional nas variáveis de parâmetro das Procedures, confirmada como persistida pela sonda; a variável do API Object continuou sobrescrita; `requestBody` saiu `false`;
3. terceira execução - corrigida a sobrescrita no `ApiPlanListProcedureWriter`; variável do API Object com `Required='True'`; `requestBody` saiu `true`.

Como a única diferença entre a segunda e a terceira execução foi a variável do API Object, ela é a causa do efeito. Marcação em item de SDT e em variável de parâmetro de Procedure não produzem efeito no YAML e foram removidas. Uma quarta execução, com a DLL final já sem essas marcações e sem a sonda, confirmou que `requestBody: required: true` se mantém.
