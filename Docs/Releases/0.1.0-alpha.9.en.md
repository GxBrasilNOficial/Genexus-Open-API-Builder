## Attention — List HTTP contract change

If you already generate APIs with this extension and consume the **List** endpoint, read this before upgrading.

Starting with `0.1.0-alpha.9`, the `List` body no longer uses the `ListResponse` envelope. Fields are returned at the **root** of the JSON:

| Situation | Body |
| --- | --- |
| Success | `Items`, `Pagination`, `AppliedFilters`, `ErrorResponse` |
| Validation error (e.g. invalid `pageSize`) | the same shape, with `ErrorResponse` populated |

**This applies to every API regenerated with this version, whatever generator the environment uses** (including Java and others beyond .NET). There is no “.NET-only” vs “legacy Framework” branch: the extension emits the same flat contract everywhere.

**Breaking change.** Callers that read `body.ListResponse.Items` (or equivalent) must update the client and re-run the Wizard (or Sync) on each generated API.

### Why we changed it (not a design preference)

On GeneXus 18 (measured on U15), the **REST wrapper generated by .NET** specially handles an `out` whose SDT contains a **collection** — the typical `List` case, with `Items`:

- on success, it unwraps the SDT and returns only the inner content;
- `ErrorResponse` no longer appears consistently in the HTTP body;
- the YAML still advertised `ListResponse` + `ErrorResponse`, but the real .NET JSON **did not** match .NET Framework.

The motivating defect was measured **only** on that .NET generator. On Framework the old `ListResponse` envelope was stable. We still unified the contract in the extension: one shape for BFFs/clients, aligned with the YAML, without depending on one generator’s asymmetric behavior.

We tried workarounds that would keep `ListResponse` (including a third `out` and SDT shape variations). **With an items collection — the shape List needs — the unwrap returns.** The stable path we validated was to drop `ListResponse` from the public contract and expose flat outs. On reapply, the extension deletes an orphan `*ListResponse` SDT when it owned it.

Without that, BFFs/front ends outside GeneXus cannot get one contract across environments.

### What we validated in this Alpha

HTTP smoke and body parity on:

- .NET Framework / SQL Server
- .NET / PostgreSQL

On **Java and other generators**, the **generated** contract is the same; we did **not** exercise runtime parity ourselves in this release — if you publish on those environments, verify a List `GET` after reapplying the Wizard.

Nuance: on .NET Core, empty `AppliedFilters` or empty collections may be omitted from JSON; treat absence as “empty”, not as a contract error.

### What to do when upgrading

1. Install this release’s DLL (pick U14+ or U13− below).
2. In the KB, reopen the **Wizard** (or **Sync**) on each generated API and apply `List` again.
3. Update OpenAPI clients/generators that still navigate `ListResponse`.
4. Run `Build All` on the environments you publish and check a List `GET` — especially if you use Java or another generator beyond the two .NET ones above.

Technical detail and evidence: [B120 plan](../Implementation/2026-09-10-B120-ENVELOPE-HTTP-LIST-MULTIPLATAFORMA.md) and [IDE/HTTP acceptance](../Implementation/2026-09-24-B120-ACEITE-IDE-SMOKE-HTTP.md).

## You must choose the correct DLL

Download and install only the file that matches your IDE version:

| GitHub Release asset | For | Not for |
|---|---|---|
| `GenexusOpenApiBuilder.Extension.dll` | GeneXus 18 Upgrade 14, Upgrade 15, and later (**U14+**) | GeneXus 18 **U13−** (Upgrade 13 and earlier) |
| `GenexusOpenApiBuilder.Extension-gx18u13.dll` | GeneXus 18 Upgrade 13 and earlier (**U13−**) | GeneXus 18 **U14+** |

The `-gx18u13` suffix exists to distinguish the public download. Do not rename a DLL to make it look like another line, and do not install both DLLs in the same IDE. The **U13−** line is formally validated on Upgrade 13; earlier upgrades may work, without a complete test matrix in this Alpha.

## Installation

Follow the [public installation guide](../Public/INSTALL.md). In short:

1. choose the DLL from the table above;
2. with the GeneXus IDE open, use **Extensions Manager → Add > Local**;
3. close the IDE completely;
4. run `genexus /install` in the matching installation;
5. reopen the IDE, check the menus, and **re-apply List** on existing APIs.

The GitHub Packages `.nupkg` is not the IDE installer. For public install, use the Release DLL asset.

## Known limitations

- Flat List contract: HTTP validation in this Alpha on the two .NET generators; Java and other generators get the same generated contract without our runtime matrix in this release.
- KB preferences may still re-check generation checkboxes on reencounter (`B108`, parked).
- Intermittent Apply failure family on very large KBs under investigation (`B109`, including branch C).
- Continuing an interrupted Apply/Sync is out of scope; use Recover to discard the record, then Wizard or Remove.
- Sublevel limitations from `0.1.0-alpha.5` remain.
- Native GeneXus OpenAPI YAML keeps the limitations documented in [B088](../Implementation/2026-08-10-B088-LIMITACOES-YAML-NATIVO.md).
- On IIS + .NET Framework, `PUT` and `DELETE` require the handler adjustment described in the [README](../../README.md#requisito-de-ambiente-put-delete-e-patch-em-iis).
- Alpha is still not Beta.
