## Atención — cambio en el contrato HTTP del List

Si ya genera APIs con esta extensión y consume el endpoint **List**, lea esto antes de actualizar.

A partir de `0.1.0-alpha.9`, el cuerpo del `List` deja de usar el envelope `ListResponse`. Los campos pasan a salir **en la raíz** del JSON:

| Situación | Cuerpo |
| --- | --- |
| Éxito | `Items`, `Pagination`, `AppliedFilters`, `ErrorResponse` |
| Error de validación (p. ej. `pageSize` inválido) | el mismo diseño, con `ErrorResponse` relleno |

**Esto vale para todas las APIs regeneradas con esta versión, sea cual sea el generador del environment** (incluido Java y otros además de los .NET). No hay rama «solo .NET» frente a «Framework antiguo»: la extensión emite el mismo contrato flat en todos.

**Breaking change.** Quien leía `body.ListResponse.Items` (o equivalente) debe ajustar el cliente y reaplicar el Wizard (o Sincronizar) sobre cada API generada.

### Por qué cambiamos (no fue preferencia de diseño)

En GeneXus 18 (medido en U15), el **wrapper REST generado por .NET** trata de forma especial un `out` cuyo SDT contiene **colección** — el caso típico del `List`, con `Items`:

- en el éxito, «desenvuelve» el SDT y devuelve solo el contenido interno;
- el `ErrorResponse` deja de aparecer de forma consistente en el HTTP;
- el YAML seguía anunciando `ListResponse` + `ErrorResponse`, pero el JSON real en .NET **no** coincidía con el de .NET Framework.

El defecto motivador se midió **solo** en ese generador .NET. En Framework el envelope antiguo con `ListResponse` era estable. Aun así unificamos el contrato en la extensión: una sola forma para BFF/clientes, alineada al YAML, sin depender del comportamiento asimétrico de un generador.

Probamos contornos que preservarían `ListResponse` (incluido un tercer `out` y variaciones del SDT). **Con colección de ítems — el diseño que el List necesita — el unwrap vuelve.** El camino estable que validamos fue abandonar `ListResponse` en el contrato público y exponer outs flat. En el reapply, la extensión elimina el SDT `*ListResponse` huérfano cuando era de su propiedad.

Sin eso, BFF/front fuera de GeneXus no logran un contrato único entre environments.

### Qué validamos en esta Alpha

Smoke HTTP y paridad de cuerpo en:

- .NET Framework / SQL Server
- .NET / PostgreSQL

En **Java y demás generadores**, el contrato **generado** es el mismo; la equivalencia runtime **no** la ejercimos nosotros en este release — quien publique en esos environments debe verificar un `GET` de List tras reaplicar el Wizard.

Matiz: en .NET Core, `AppliedFilters` vacío o colecciones vacías pueden omitirse del JSON; trate la ausencia como «vacío», no como error de contrato.

### Qué hacer al actualizar

1. Instale la DLL de este release (elija U14+ o U13− abajo).
2. En la KB, reabra el **Wizard** (o **Sincronizar**) sobre cada API generada y aplique de nuevo el `List`.
3. Actualice clientes/generadores OpenAPI que aún navegan por `ListResponse`.
4. Ejecute `Build All` en los environments que publica y verifique un `GET` de List — en especial si usa Java u otro generador además de los dos .NET anteriores.

Detalle técnico y evidencia: [plan B120](../Implementation/2026-09-10-B120-ENVELOPE-HTTP-LIST-MULTIPLATAFORMA.md) y [aceptación IDE/HTTP](../Implementation/2026-09-24-B120-ACEITE-IDE-SMOKE-HTTP.md).

## Elija obligatoriamente la DLL correcta

Descargue e instale solamente el archivo correspondiente a la versión de su IDE:

| Asset en GitHub Release | Sirve para | No sirve para |
|---|---|---|
| `GenexusOpenApiBuilder.Extension.dll` | GeneXus 18 Upgrade 14, Upgrade 15 y posteriores (**U14+**) | GeneXus 18 **U13−** (Upgrade 13 y anteriores) |
| `GenexusOpenApiBuilder.Extension-gx18u13.dll` | GeneXus 18 Upgrade 13 y anteriores (**U13−**) | GeneXus 18 **U14+** |

El sufijo `-gx18u13` existe para distinguir la descarga pública. No cambie el nombre de una DLL para hacerla pasar por otra línea y no instale las dos en el mismo IDE. La línea **U13−** fue validada formalmente en el Upgrade 13; upgrades anteriores pueden funcionar, sin matriz de prueba completa en esta Alpha.

## Instalación

Siga la [guía pública de instalación](../Public/INSTALL.md). En resumen:

1. elija la DLL según la tabla;
2. con la IDE GeneXus abierta, use **Extensions Manager → Add > Local**;
3. cierre completamente la IDE;
4. ejecute `genexus /install` en la instalación correspondiente;
5. reabra la IDE, verifique los menús y **vuelva a aplicar el List** en las APIs existentes.

El `.nupkg` de GitHub Packages no es el instalador de la IDE. Para la instalación pública, use el asset DLL del Release.

## Limitaciones conocidas

- Contrato flat del List: validación HTTP de esta Alpha en los dos .NET; Java y demás generadores generan el mismo contrato sin matriz runtime nuestra en este release.
- Las preferencias de la KB aún pueden volver a marcar checkboxes de generación en el reencuentro (`B108`, estacionado).
- Familia de fallos intermitentes de Apply en KB muy grande bajo investigación (`B109`, incluido ramo C).
- Continuación de Apply/Sync interrumpido fuera de alcance; use Recuperar para cerrar el registro y después Wizard o Remover.
- Las limitaciones de subniveles de `0.1.0-alpha.5` permanecen.
- El YAML OpenAPI nativo de GeneXus mantiene las limitaciones documentadas en [B088](../Implementation/2026-08-10-B088-LIMITACOES-YAML-NATIVO.md).
- En IIS + .NET Framework, los verbos `PUT` y `DELETE` exigen el ajuste del handler descrito en el [README](../../README.md#requisito-de-ambiente-put-delete-e-patch-em-iis).
- La Alpha aún no es la Beta.
